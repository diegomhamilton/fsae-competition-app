Inspection Event PR Review Plan

Use operations-first SPDD prompts to keep feature work reviewable without forcing every subtask into a tiny PR. The default is one feature branch and one PR per major feature, with task-sized commits and task branches only when review scope gets too broad.

Decision Rule

Stay in one PR One product outcome, fewer than 10 changed files, one main reviewer context, and validation can be explained in one concise PR description.
Split into task branches More than 10 changed files, multiple domains such as persistence plus UI plus tests, project-file churn, or high-complexity async/coordinator behavior.
Squash back before review Use task branches for development isolation, then squash them into the feature branch so the final PR remains one coherent story.

Common Operations Across Prompts

  • Use OpenSpec tasks, design, specs, and the feature file as the acceptance source.
  • Write the PR description with Summary, Scope, Notes, and Validation.
  • Keep commits task-sized, preferably one subtask or tightly related pair per commit.
  • Add failing tests before implementation for model, service, coordinator, persistence, and validation behavior.
  • Use stable accessibility identifiers rather than localized labels in UI tests.
  • Do not claim manual validation unless actual app evidence is recorded.
  • Split when one PR mixes unrelated reviewer questions, even if the file count is below 10.

TASK#7 PR Operations

Feature branch: codex/inspection-event-session-flow

PR Slice Operation Summary Review Minimizer
Coordinator tests and coordinators Start with failing tests for login, routing, session start/resume, stage selection, team switching, and restore. Implement coordinators in task branches if needed. Keep each coordinator reviewable. Split when all four coordinators plus tests exceed 10 files.
JSON persistence and schemas Define Codable draft/submission schemas, then implement actor-isolated Application Support JSON persistence with one draft file per test case. Separate schema review from atomic file-write behavior if both are large.
Store, submissions, rechecks, stickers Add actor-isolated event store, immutable submission snapshots, recheck lifecycle, and sticker eligibility calculation. Keep service PR slices independent when APIs are still changing.
Coordinator-backed views and validation Bind existing SwiftUI views to coordinator-backed state and manually validate start, restore, submit, blocked submit, team switch, rechecks, and sticker eligibility. Split UI binding from service implementation if view changes obscure logic review.

TASK#8 PR Operations

Feature branch: codex/inspection-event-ui-tests

PR Slice Operation Summary Review Minimizer
Launch fixtures Add positive, negative, and edge mock launch states after stable identifiers and navigation hooks exist. Split fixture plumbing if it touches runtime app code and test project setup together.
UI automation flows Cover login, session selector, stage navigation, case navigation, step editing, validation blocking, team switching, recheck review, and sticker eligibility. Group flows by reviewer context and avoid one giant UI test file.
Identifier assertions Assert required controls and statuses through stable accessibility identifiers instead of localized labels. Split if app code needs identifier fixes before test assertions can land.
Snapshots and coverage docs Add practical snapshots and document coverage back to feature scenarios and personas. Split baselines or dependency setup if snapshot diffs dominate the PR.

TASK#9 PR Operations

Branch: codex/inspection-event-docs-review-hygiene

PR Slice Operation Summary Review Minimizer
Frontmatter and report Add YAML frontmatter and write the technical report overview for architecture, rechecks, testing, accessibility, and localization. Keep documentation-only unless code examples require tested changes.
Tutorials Add short tutorials for JSON fixtures, validation rules, accessibility identifiers, and persona scenarios. Split tutorials by topic if examples become implementation work.

Commit hygiene Split tasks across distinct commits so each completed task or related pair has a reviewable checkpoint. Use commits for history, task branches for review isolation, and one feature PR for final review.

Operational Template

Summary: one sentence naming the user-visible operation.

Scope: changed files grouped by reviewer concern, not by implementation chronology.

Notes: design constraints, split decisions, known limitations, and follow-ups.

Validation: test command output or explicit manual validation evidence. Use not run honestly when evidence is not available.
